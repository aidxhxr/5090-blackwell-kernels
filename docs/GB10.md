# GB10 (DGX Spark) hardware sheet (secondary target)

This repo was written for one machine: an NVIDIA DGX Spark, whose GPU is the GB10 "Grace
Blackwell" superchip. Mine is still on order, so the primary target is now the RTX 5090
([RTX5090.md](RTX5090.md)) and the GB10 is the second machine, to be benchmarked when it
arrives. The tuning constants in the kernels were reasoned from the numbers on this page, and
these are the numbers the GB10 roofline and "% of peak" columns will be based on. Same
kernels, same programming model, a memory system 6.5× slower than the 5090's: that contrast is
the reason to keep both.

## Specs

| Item | Value | Where it comes from |
|---|---|---|
| Superchip | GB10: Blackwell GPU + 20-core Arm v9 CPU (10× Cortex-X925 + 10× Cortex-A725), one package | NVIDIA product page |
| Compute capability | **12.1 → `sm_121`** | `deviceQuery` / `torch.cuda.get_device_capability()` |
| SMs / CUDA cores | 48 SMs × 128 = **6,144 CUDA cores** | `deviceQuery` |
| GPU boost clock | ≈ 2.42 GHz | `nvidia-smi -q -d CLOCK` |
| Memory | **128 GB LPDDR5X, unified** (CPU and GPU share it), 256-bit @ 8,533 MT/s | NVIDIA |
| Memory bandwidth | **273 GB/s** (theoretical) | NVIDIA spec |
| L2 cache | 24 MB | `deviceQuery` |
| fp32 (CUDA cores) | ≈ **31 TFLOPS** theoretical = 6,144 × 2 FLOP × 2.42 GHz | derived |
| bf16 / fp16 tensor, fp32 accumulate, dense | ≈ **213 TFLOPS** measured with an `mma.sync` micro-benchmark | community measurement (NVIDIA forums) |
| fp8 dense | ≈ 214 TFLOPS measured | same |
| fp4 | up to ≈ 1 PFLOP (with sparsity; NVIDIA's headline number) | NVIDIA |
| CUDA toolkit | **13.0 or newer** (the first release that knows `sm_121`) | CUDA release notes |
| fp8 build | the fp8 GEMM and `bench_peak` compile for **`sm_121a`** (`ARCH=121` maps to it): the block-scaled `mma.sync.kind::mxf8f6f4` that runs fp8 at full rate on the 5090 is only exposed on the arch-specific target, and whether the GB10 has the same half-rate plain fp8 path is one of the first things to measure | [fp8gemm](design/fp8gemm.md) |
| OS | DGX OS (Ubuntu-based), aarch64 | — |

The tensor-core figure is what `mma.sync` reaches in a tight loop, so it is the honest
ceiling for the `hgemm` kernel here; NVIDIA does not publish a dense bf16 TFLOPS number for
the GB10 the way it does for datacenter parts.

## Ridge points

Arithmetic intensity at which a kernel stops being memory-bound:

| ceiling | ridge point |
|---|---|
| fp32 CUDA cores | 31 TFLOPS ÷ 273 GB/s ≈ **114 FLOP/byte** |
| bf16 tensor cores | 213 TFLOPS ÷ 273 GB/s ≈ **780 FLOP/byte** |

For comparison an H100 SXM sits around 3.35 TB/s, so its bf16 ridge is ~300 FLOP/byte. The
GB10 has a lot of compute per byte of bandwidth, which drives two design choices in this repo:

- Memory-bound LLM kernels (RMSNorm, SwiGLU, softmax) can never do better than 273 GB/s, so
  they are reported as **% of DRAM bandwidth**, and fusing passes (`add_rmsnorm`) is worth
  more here than on an HBM part.
- A bf16 GEMM needs large block tiles and real data reuse in shared memory and registers to
  reach the tensor-core roof; a 4096³ GEMM has an intensity of ~1,365 FLOP/byte so it *can*
  be compute-bound, but only with a proper pipeline (see `hgemm` variant 2).

## `sm_121` is not `sm_100`

NVIDIA's compute-capability table splits Blackwell into:

| CC | parts | tensor-core programming model |
|---|---|---|
| 10.0 (`sm_100`) | B200 / GB200 datacenter | `tcgen05` instructions, TMA, thread-block clusters, Tensor Memory |
| 12.0 (`sm_120`) | RTX 50-series / RTX PRO Blackwell (incl. the RTX 5090, this repo's primary target) | `mma.sync` (Ampere-style), `cp.async`, no `tcgen05` |
| **12.1 (`sm_121`)** | **GB10 (DGX Spark)** | same family as 12.0 |

Consequences for this code base:

- We use the **WMMA / `mma.sync`** path (`<mma.h>`, `nvcuda::wmma`), which is supported
  from `sm_80` upward and is the right path for `sm_120`/`sm_121`.
- We use **`cp.async`** (Ampere+) for global→shared staging. No clusters, no
  `tcgen05` — those would fail to compile or load on the GB10.
- Libraries that ship SASS only for `sm_100` will not run here; libraries that ship PTX for
  `sm_120` usually JIT fine. Building from source with `-gencode arch=compute_121,code=sm_121`
  avoids the JIT entirely.
- Shared memory: we keep every kernel ≤ 48 KB static shared memory so no
  `cudaFuncSetAttribute` opt-in is needed.

## Build flags used here

The build defaults to `sm_120` now, so the Spark needs the arch spelled out (`make build
ARCH=121` is the short form of the first command; `ARCH="120;121"` builds for both):

```bash
# CMake (bench binaries + static lib)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=121
cmake --build build -j

# PyTorch extension
TORCH_CUDA_ARCH_LIST="12.1" pip install -e . --no-build-isolation
```

`-lineinfo` is on by default so Nsight Compute can map stalls back to source lines without
the cost of `-G`.

## Verify on your box

```bash
nvidia-smi                                     # driver + "NVIDIA GB10"; memory shows N/A (unified)
nvcc --version                                 # must be 13.x
/usr/local/cuda/extras/demo_suite/deviceQuery  # CUDA Capability 12.1, 48 multiprocessors
free -h                                        # unified memory usage lives here, not in nvidia-smi
python3 -c "import torch; print(torch.cuda.get_device_name(), torch.cuda.get_device_capability(), torch.version.cuda)"
```

Expected: `NVIDIA GB10 (12, 1) 13.x`. If PyTorch prints a CUDA version below 13 it cannot
load `sm_121` kernels; install a CUDA-13 wheel.

## Measuring your own ceiling

`bench_bandwidth` (in `build/`) copies a large fp32 array and reports achieved GB/s; on a
DGX Spark expect roughly 200–240 GB/s, i.e. 75–90 % of the 273 GB/s spec (an expectation, not
yet run). That measured number is the realistic roof for the row-wise kernels, so treat
"% of 273 GB/s" as conservative.
